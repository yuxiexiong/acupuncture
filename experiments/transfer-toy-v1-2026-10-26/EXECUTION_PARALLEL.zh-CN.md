# 迁移 toy：独立进程并行执行补充

日期：2026-10-26。用户已授权在验证有效、保持实验质量的前提下缩短运行时间并实施。本补充只调整工作分配与进程数量，原科学协议、历史记录及 `freeze.json` 所列文件保持不变。根因实验继续暂停。

## 执行变化

目标模型采用两张 H20，**每卡 3 个独立模型进程，共 6 个分片**。worker `i` 分配到 GPU `i % 2`，每个进程仅处理题号满足 `index % 6 == i` 的题目。各进程拥有独立模型对象与缓存，每次实际 forward 的 batch size 仍为 **1**。

复用原 `TransferEngine` 与生成、似然计算实现。BF16、eager attention、greedy 解码、原生 EOS 和任务停止规则、固定题目、19 个迁移条件、条件顺序、剂量、逐题校准方式及生成上限全部不变。数学与代码任务的非空停止条件也保持原实现；本次采用的并行调度不启用省略停止回调等其他优化。

每个目标仍完整执行：

- 64 题 × 19 条件的行为生成，及同样规模的能力诊断。
- 原版与事前固定的真实源 `S_recipe` 两条件，完成最新四项 Benchmark：MMLU 1,000、ARC-C 200、GSM8K 100、HumanEval 100，共 **1,400 对、2,800 个题目—条件单元**。
- 原有官方评分、HumanEval 沙箱、完整原文导出和匿名人工评判材料。机器阶段完成不等于人工行为判定完成。

新增 `run_toy_parallel.py`、`run_benchmark_parallel.py`、`finish_benchmark_parallel.py`、`export_results_parallel.py` 实现分片与完整性核验，记录新脚本哈希、原冻结清单哈希、分片拓扑及各 worker 回执。原有脚本与失败/完成记录保留。分片调整不增加或减少样本，也不根据回答选择条件。

## 实施前的一致性与吞吐验证

9B 独立验证使用相同的固定工作负载，比较单进程与同卡多个独立进程。每个 worker 的验证负载包含 7 次生成调用，以及 `T_0`、`S_recipe` 条件下的四候选似然检查；输入包含 1,066 token 的较长上下文，最长生成预算为 512 token。

| 同卡进程数 | 完成的生成 token 总数 | 测得墙钟时间 | 相对单进程的总吞吐 |
| --- | ---: | ---: | ---: |
| 1 | 1,468 | 107.689 秒 | 1.000× |
| 2 | 2,936 | 114.864 秒 | 约 1.875× |
| 3 | 4,404 | 151.387 秒 | 约 2.134× |

并行各 worker 与单进程参考的全部生成 token、结束信息及上述候选似然读数均完全一致。此处吞吐按同时完成的总工作量除以墙钟时间计算；三进程中的单条请求延迟可以增加，而总吞吐提高。

另有 **4 项 CPU 集成测试通过**，核验 2/4/6 分片的分配、完整记录与导出、缺失/篡改拒绝，以及固定 Benchmark 的分片和原始执行/评分顺序。CPU 测试不代替 GPU 数值一致性验证。

以上证据支持采用已测试的三进程配置，但不是对所有提示、所有长度和所有条件的穷尽证明，也不证明每卡 3 进程是全局最优配置。测得约 2.134× 的验证负载吞吐增益不能直接当作全队列加速倍数；模型装载、题目长度、提前结束、诊断、沙箱和导出均需计入实际耗时。

## 队列、证据与后续核验

共享源 4B 的现有两进程采集继续原样运行并等待完成，**不得为并行化重跑源采集**。仅替换后续队列调度，复用源模型完成回执及其哈希绑定的校准记录。

顺序保持为：源 4B 完成 → 9B 迁移采集 → 9B 四项 Benchmark → 评分及导出完成 → 2B。2B 在正式采集前必须完成自身的单进程/并行一致性验证；9B 的验证结果不能替代 2B 的验证。若验证失败，保留记录并回到已验证的执行方式，不放宽题目、剂量、预算或评分要求以获得通过。

每个 worker 单独核验权重未变与钩子移除；收尾核验所有题目—条件记录唯一且完整、源校准一致、token 与文件哈希一致。发现实现问题时保留原尝试，用单独版本/尝试修复，不能覆盖历史结果。

继续每 30 分钟报告实际阶段、完成数、两卡状态及预计完成时刻。ETA 根据当前真实进度和各阶段实测耗时更新，不在本补充中固定结束时间。最终报告实际总耗时及 ETA 偏差，人工双盲行为评判的等待时间另记。
