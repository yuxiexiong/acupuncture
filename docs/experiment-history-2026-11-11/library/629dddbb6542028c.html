1. 作者到底用什么检查和对比权重

原作者名称是Astra，调用标识为OpenAI gpt-6-astra，推理档位max。第一轮run.json记录了以下关键参数（只摘录，不是当前可直接运行的完整命令）：

codex exec --json -m gpt-6-astra
-c model_reasoning_effort="max"

具体分工： 1. 作者调度程序启动/续接Codex CLI，发送任务与上一轮反馈。 2. Astra提出诊断、生成Python代码或forward请求，阅读数值摘要和文字结果并决定下一步。 3. 作者的持久CPU Python内核读取完整权重并执行数值分析/编辑；不是把全部4B权重以文本一次塞进Astra上下文。 4. 单独forward服务运行被编辑的Qwen，返回原版/候选的生成、评分与内部读数。 5. 作者程序将结果作为下一轮反馈再送给Astra。

因此“用Codex CLI”与“用远程模型服务”不矛盾。公开run.json没有提供足够信息确定作者使用API key、ChatGPT登录或其他接入/计费安排；不能从codex exec推断付费方式。官方文档说明Codex CLI支持ChatGPT登录和API key。此官方说明是可用认证方式，不是作者认证方式的证据。

我们的默认路线保持Codex CLI + gpt-6-astra/max + 自建最小harness；先只读确认登录方式和实际可用模型，再在执行合同中固定。当前没有切换账号、读取/输出密钥或发起付费模型调用。若无法用原模型，明确列为替代编辑器实验，不静默换名。直接改用API SDK会改变调用包装/上下文管理，不能不说明便称为原调用栈复现。

研究问题是“相同方法在两种模型上怎样工作”，不是“把0.8B补丁映射到4B”。跨模型只汇报各自相对原版的变化与过程差异；两模型不能支持参数规模的因果规律，一次搜索不能估计稳定成功率。

4. 4B从什么问题开始，怎样确认有效

目标仍为提高数学任务表现。第一次诊断由4B搜索者在自己的预算内进行： - 观察错误答案、完成但无答案、截断/重复等失败类别； - 自行选择有证据的候选，不由观察者指定“4B也一定是循环病”； - 不先扎针造出失效，再宣称修好了原版4B； - 如果原版4B已较好，提升空间小也是结果；不人为削弱原版或换更难题后继续称同一协议。

同一practice池可在两次独立搜索中使用，但每个搜索者仅看自己的结果，自行登记开发/确认题目；禁止把A已知有效题或补丁反馈给B。主评测题集在任何搜索阶段都不可见。

两轮分别记录所有候选、预测、代码、失败、逐题原文、实际请求的张量与成本，沿v1的完整过程日志规则。最终冻结后，各自比较原版和本次最终版： - 主终点：MATH500、GSM8K的avg@n正确率； - 分开看错转对/对转错、截断、无答案、长度和其他基准； - 以题为聚类单位给不确定性，不能把同题多次采样当独立题； - 4B改动比例、范数、行为改善不能和0.8B直接当同等强度；若两者结果不同，只报告条件性差异； - 只有本次实际完成的对照支持相应机制措辞，补丁有效不等于唯一病因。

允许0.8B有效/4B无效、两者都有效但路径不同、仅部分基准提升、两者都无效。各自50pass后结束，不因为4B结果弱而自动加预算或移植A的答案。

5. 预算与资源调度

  • 共两次独立搜索：100个成功forward，最多600次Python；每次generation仍至多512回答，both每模型至多256；teacher-forced沿v1的文本/token及6GB返回限制。
  • 同样pass数是同等工具调用上限，不是同等token用量、计算量或费用。实际token、被分析张量字节、CPU/GPU设备秒、模型重载与编辑器消耗分别列账。
  • 4B较大，使用物理microbatch可避免OOM，但不能悄悄降低逻辑请求容量或把一批拆成多个可见科学pass。请求执行完成后才一次返回并计1pass；seed、分片顺序及批处理差异需冻结，不能许诺跨引擎随机轨迹完全相同。
  • 若所请求张量超过原6GB上限，按原合同拒绝并说明尺寸；不得偷偷裁剪。该限制使4B单位pass可读的信息不同，这是资源边界，不补称两模型完全相等的信息预算。
  • 模型工程验收拟各至多0.5 GPUh，合计1.0 GPUh；这只是准备预算，当前未运行。正式GPUh/墙钟/编辑器费用上限须分别经过吞吐测量后填写，不能用参数量5倍或作者20.3小时倍乘。
  • 两轮完整十项终验各25792回答，合计51584份（四个模型状态）。不额外跑作者最终补丁、不新增10/25-pass搜索。
  • 一次只运行一条主要搜索，优先用空闲设备做该轮生成/诊断；另卡能否承担终验分片取决于实测资源。现有H20空闲快照会过时，开跑前重新检查，不能干扰其他任务。
  • 两轮累计输出可能超过现有工作盘；按候选差分保存、压缩并校验后归档，正式前冻结存储路径与空间门槛。失败原文和请求张量不能因空间不足无记录删除。

6. 设计卡与C01–C14增补自查

规范：已重新读取experiment-design-self-check v1。审查者：同一助手，非独立评审。v1自查继续有效的共同规则以链接引用，本节审查实际改变的范围。

设计卡： 1. 主线：WSP全过程研究；新增问题是该方法在原始4B上的自身诊断/修改是否有效。 2. 增量：得到独立4B搜索过程、原版到最终版的效果和失败边界；不承诺“规模规律”。 3. 依据/反例：原作者0.8B流程、不同预算不同补丁及Gemma弱增益；4B旧激活针结果不是本次静态编辑证据。 4. 操作：两模型各从指定revision原版独立搜索，除模型真实结构/资源适配外保持共同工具合同；无供体、无跨模型补丁、无训练。 5. 估计对象：每模型内最终权重修改相对本模型原版的总效果；两轨迹作描述性比较。 6. 判读：成功/阴性/部分/异号按各基准保留；工程未过不可判，不把差异归因为参数规模。 7. 成本：共100pass/至多600Python/51584终验回答；正式时长费用尚需实测；无重复全模型扫描。 8. 退出：各自预算完成或资源/信息/身份错误暂停；不自动追加第三模型或抄0.8B补丁补救。

Codex CLI被说成“无需API/免费”。 → 只据原日志说明客户端和模型；认证、额度、费用另核实，不作免费或API key断言。
