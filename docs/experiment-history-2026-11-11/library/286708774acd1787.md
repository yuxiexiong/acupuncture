# NMT-01 决策日志

**D1（冻结前）方案入库。** v2 方案与自查原在分支 `codex/nmt-01-norm-match-v2`（`f837ad68`），按用户“只上 main”的规则逐字复制到 main 的 `docs/cache-increment-norm-match-v2-2026-11-03/`，原分支不动。

**D2（冻结前）评审修正的落实方式。** 合同 §0 的三处修正按 2026-11-03 评审商定写入：I_S 标注阈值取 [0.8, 1.25]（输入中位数、拼接范数比），只用于标注、不改变主标签；RND 写入轴取运行中按 custom update 同样方式归一化的 k_b；零范数“源零、目标非零”抛 Unmatchable，停整轮。

**D3（冻结前）已核实的 b 依赖。** SIT 正式记录 5376 行：第 13 层 ΔS 范数与 b 无关（差 0），第 14 层起各层最大相对差 3%–23%（第 28 层最大）。原因是 b 改了第 13 层的写入键，从而改了 t1 输出与下游输入。因此逐 b 匹配不保证 I_S 等幅，合同要求报告 I_S 描述量。

**D4（冻结前）一阶参照的计算方式。** 用 NBR 已存的每头 XA（读者为接收背景 (r,0,b)）与 g，在两个线性化点（(r,0,b) 与 (r,1,b)）计算，结果冻结在 `readiness/first-order-ref-r01.json` 并列入冻结清单。计算发生在任何 NMT 模型输出之前。第 13 层的缩放系数按直接复制取 1。

**D5（冻结前）分析端修复。** CPU 端到端测试发现 `nmt_analysis.py` 的 bootstrap 抽样字典键写成 `tnf`，消费方用 `main_tnf`，会让分析在真实数据上崩溃。冻结前修复，测试改为通过。

**D6（冻结前）预检设备时间上限。** 方案写“预检及所有冒烟合计 0.15 GPUh”；代码把预检上限设为 0.12，冒烟单独计时并在收据中记录，二者合计不超过 0.15。

**D7（冻结前）冒烟 r01 失败后的修复。** 真实模型冒烟在 RND 构造处报设备不一致：ρ̂ 在 CPU 上生成（为了可复现和计算 hash），而写入键与增量在 GPU 上。修复：ρ̂ 仍在 CPU 生成并计算 hash，相乘前搬到写入键所在设备。只改设备，不改数值定义。失败的冒烟输出没有生成文件（脚本在写文件前退出），没有写出任何 M/Y。修复后重跑冒烟（r02）。

**D8（冻结前）冒烟 r02 两道闸门失败后的修复。** RND 范数误差 3.5e−4（门槛 1e−6）、k̂ 秩一残差 7.1e−4（门槛 1e−4）。原因相同：冻结的 custom update 用 x·rsqrt(Σx²+eps) 归一化写入键，内核实际用的键范数比 1 小约 3.5e−4；秩一残差按单位向量投影，偏差翻倍为约 7e−4。写入轴本身正确。修复：取内核实际写入键的方向再精确单位化（rnd_block 与 rank1_residual 都改），合同 §0 第 2 条与 §3 表格措辞相应改准。其余闸门在 r02 中全部通过（UP/DN/UPG 缩放误差 ~1e−16，cast 2.9e−8，oracle 1.6e−7）。冒烟 r02 在写文件前退出，没有写出 M/Y。修复后重跑冒烟（r03）。
