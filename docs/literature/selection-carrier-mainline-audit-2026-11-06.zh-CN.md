# 七步查重：主线候选"稀疏干预怎样改变答案选择的来源"

2026-11-06。检索由本会话四个子代理并行执行，主会话整理并亲自复核了最近邻 2611.01909。**这是覆盖报告，只回答"先例给到哪里、哪里在本轮没找到"，不给等级。** 一轮检索，约 155 条查询（网页检索 109、OpenReview 10、arXiv API 36），外加五篇近邻的引用链。

## 被查的主张

对象：Qwen3.5-4B（全注意力层与 Gated DeltaNet 层交替；GDN 层有递推状态 S 和卷积缓冲）。任务：上下文内记录查找。

1. 答哪一条记录（"选择"）在答案时刻由不止一个状态来源提供：提示期形成的递推状态；第一个答案步由末尾卷积缓冲 V 通道驱动的写入；随后的递推读取把它变成答案。
2. 稀疏激活干预改变答案，不是删掉选择，而是改变哪个来源的选择到达读取；来源都受损时落到首列记录。
3. 换入另一输入的来源，答案跟随供体的选择（看起来是供体的列表位置），是否跟随取决于接收者其他来源是否完好。

## 坏消息先说

1. **干净模型那一半已经发表，而且就在同一模型族上。** 2611.01909《Who Asks, Who Answers》（2026-11-01，主会话已复核原文）：8 对键值查找，供体与宿主同一字典、不同查询键。把第 16–18 层（"Address"块）的供体递推状态在倒数第二个 token 后换入宿主，检索跟随供体 0.99（9B，§5.2）。Qwen3.5-4B 只出现在规模表（§7、表 3）：移植该块的**末位置输出**重定向 0.70，移除该块后准确率仍 0.94，作者归因后面的读取层补偿；**4B 上没有报告递推状态移植，4B 的层号也没有给出**（更正见文末）。结论："线性注意力构造查询，softmax 注意力执行查找。"我们 NSR-01 的"换入供体递推状态 32/38 跟随供体"是同类实验的同向结果，不能再当发现写。
2. **"位置跟随"在这个模型上已有数字。** 2609.38530 附录 E（作者标注初步）把 Gur-Arieh 的位置/词汇/自指协议跑到 Qwen3.5-4B 上，位置份额 0.72，残差流层面。稠密 Transformer 上位置跟随是四篇以上正文读过的论文的共同结果（2510.06182、2402.14811、2409.05448、2505.14685），2610.00910 还报告了首个提及项最容易到达。
3. **另一类混合模型上的结论是"跟键不跟行"。** 2609.32942《The Key Handoff》在 Mamba-2 混合模型上把键与行交叉："The read is addressed by the key, not by the row."没有 GDN 模型。我们写"供体的列表位置"之前必须做键 × 行交叉。
4. **有一篇在审稿件方向相反。** ICLR 2027 投稿《From Recurrent Computation to Attention Memory in Hybrid Language Models》（只读到摘要）：提示期替换递推块贡献后，恢复原递推状态，答案偏好的变化大部分仍在，改动过的 KV 保留 67–93%，称"compute-commit-retrieve"。与我们"只恢复深层 S 48/48、只恢复深层 KV 3/48"表面相反，未读正文，口径未对，不登记矛盾。
5. **卷积缓冲不是独立记忆（推导档，据 HF 源码与 GDN 论文）。** 缓冲缓存的是最后几个位置层输入的 q/k/v 投影，进卷积后才分出 q、k、v。换缓冲等价于在 q/k/v 通路上换最后几个位置的层输入。同一步的读取已经包含该步的写入，所以"下一步读取"不是架构必然；我们观察到的 t2 很可能与编号的第一个 token 共享有关。
6. **"落到首列"本轮没找到任何机制性先例，而我们自己的随机对照削弱了它。** 同范数随机扰动也把答案推到首列。按现有证据它是选择退化时的先验，不是机制。
7. **归因在冗余下不可识别。** 2606.27510：单个中介的修补效应含交互项，要模块化的说法必须控制交互。我们"只恢复 S 48/48、只恢复缓冲 48/48"正是过度决定的情形，单项恢复只说明充分。
8. **并行风险高。** 2026-09-03 到 11-05 至少六篇混合模型检索机制论文（2609.04434、2609.15545、2609.32942、2609.33093、2611.01909、2611.08133），另有 ICLR 2027 在审稿件与一个未发表项目（SPAR"Unmixing Mechanisms"）。2611.01909 不在任何近邻的引用链上，是关键词扫出来的。

### 必打基线与对照

1. 在我们的任务上复现 2611.01909 的 Address 块状态移植与"末位置输入交换"对照，并说明我们多了什么。
2. 切点在问题之前与之后各做一次只留 KV / 只留递推，与 2609.04434 的 0.00 对上口径。
3. 每张来源表带 KV 保留与恢复臂（回应在审稿件的 compute-commit-retrieve）。
4. 供体与接收者之间键 × 行交叉，再加"编号相同、绑定重排"的第三种预测（2609.32942、2510.06182）。
5. 用"直接换最后几个位置的层输入"替代换缓冲，并在非末尾步换缓冲，说明缓冲不只是三个位置的残差窗口。
6. 同一步读取与下一步读取分开检验。
7. S、缓冲、KV 的全因子，两个方向（干净→受针、受针→干净），报告交互项。
8. 首列回退的对照：目标在首列的输入单列；打乱顺序；无问题或中性问题下模型对各记录的先验；随机同范数扰动下的回退率作零分布。
9. 失配对照：用匹配输入重采样代替平均；"同选择供体"的空操作嵌合体给失配定价。
10. 第二个模型尺寸与第二个任务族。每篇近邻都报多个模型；2611.01909 显示 4B 是冗余最多、移植率最低的一个。

### 谁会因此改做法

本轮没有找到具名的使用者。服务侧工作（2608.30310 Tail-Replay、2611.08133、2609.25053 等）已把这些状态当作可重建的瞬态处理，没有人在问"哪个来源带着选择"。也没找到谁在 Qwen3.5 上的转向或缓存方法失败、而这个结果能修。这一栏是三栏里最弱的，仍是推测档。

## 本轮没找到的（"没找到"不等于不存在）

- 稀疏或神经元级干预 × 状态来源分析 × 检索任务，在任何 GDN 混合模型上；
- 只换卷积缓冲的跨输入移植，以及缓冲内 q/k 与 V 的分开移植；
- 第一个答案 token 之后的生成步在检索任务上的写入与读取；
- 混合模型里内部扰动后落到首列记录；
- 干预条件下来源优先级的变化（所有移植论文都只用干净运行）；
- GDN 上位置与键的分离。

## 更正（2026-11-06，Codex 评估 SPF-01 合同时指出，主会话对原文 §5.2、§7、表 3 复核后确认）

初版把 2611.01909 的"4B 上 0.70"写成递推状态移植的结果。原文里 0.99 的递推状态移植只在 Qwen3.5-9B 上做过；4B 的 0.70 是 Address 块**末位置输出**的移植，论文没有 4B 的递推状态移植，也没有给 4B 的 Address 块层号（16–18 是按 9B 的编号规则推的）。影响：干净模型上"供体递推状态改变答哪一条"在 4B 上的已发表证据比初版写的弱；我们 NSR-01 在 4B 上的 32/38 仍是同向结果，但不是对某个已发表 4B 数字的重现。"必打基线"第 1 条相应改为：在我们的任务上检验同类操作，不以 0.70 为复现目标。
